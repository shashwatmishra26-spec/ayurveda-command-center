# Ayurveda Command Center — architecture & productionization notes

This document explains what's real, what's simulated, and how this
prototype maps onto a production SaaS build.

## What this is

A fully interactive prototype: 128 synthetic patients, 36 medicines across 6
suppliers, 64 appointments, 92 WhatsApp conversations, 132 orders, 122
simulated shipments, delivery exceptions, feedback, follow-ups, an AI
priority queue, a 12-agent control center, and a full audit trail — all
generated by a seeded random data engine so every run is internally
consistent. Every number on screen is clickable and drills into real
(synthetic) underlying records. No live APIs are called; the app needs
nothing but a browser.

**Everything is clearly synthetic demo data** — patient names, phone
numbers, WhatsApp threads, tracking numbers, and revenue are all generated,
and shipment tracking is explicitly labeled "Demo / simulated tracking
data" everywhere it appears.

## Under the hood

- **React** drives the whole UI — React 18 from a CDN for the live
  GitHub Pages demo, or React 19 bundled locally via esbuild for the
  offline single-file (`standalone.html`) build.
- **JSX → plain JS** via esbuild, same transform a production bundler uses.
- **Charts are hand-rolled SVG** (line/bar, single-hue sequential + fixed
  categorical hue order, hover tooltips, legends) rather than a chart
  library, so there's zero runtime dependency for data visualization.
- **Tailwind CSS** (CDN) provides the primary styling. A small first-party
  fallback engine (`fallback-utils.js`) detects if Tailwind failed to load
  (e.g. no network) and re-applies the same utility values as inline styles,
  so the app degrades gracefully instead of breaking.
- Source is modularized (`ui.jsx` = primitives/design system, `modules1-3.jsx`
  = feature areas, `app.jsx` = shell/routing/state, `data.js` = the mock data
  layer), loaded as classic scripts sharing one global scope (no bundler
  required to run it, though `dist/*.build.js` is pre-transpiled from JSX).

## Data model (entities & relationships)

```
Patient 1─* Consultation 1───┄1 Prescription *─* Medicine
Patient 1─* Appointment
Patient 1─┄1 WhatsAppConversation 1─* WhatsAppMessage
Patient 1─* PatientOrder *─* Medicine (via OrderItem)
PatientOrder 1─┄1 Shipment 1─* ShipmentEvent
Shipment 0─┄1 DeliveryException
PatientOrder 1─┄1 Payment
Patient 1─* Feedback / Complaint / FollowUp
Medicine 1─* MedicineBatch
Medicine *─┄1 Supplier
MedicineBatch 1─* InventoryTransaction
Supplier 1─* PurchaseOrder (replenishment recommendations)
WhatsAppMessage 1─┄1 AIInteraction 1─┄1 AIApproval → AuditLog
KnowledgeDocument 1─* KnowledgeReference (classical/clinic sources, verified flag)
```

Every entity that feeds an AI-generated suggestion (WhatsApp replies, refill
reminders, follow-up nudges, purchase recommendations) carries the same
lifecycle: **AI Suggested → Vaidya Approved → Sent/Executed**, logged to an
audit trail with timestamp and approver — this is enforced in the UI (see
"AI Agents → Human-in-the-loop audit trail"), not just described.

## Turning this into a real SaaS product

The prototype's mock "service layer" is `data.js` — a single module that
generates and exposes everything through one `window.AYUR` object. To
productionize:

1. Replace `data.js` with real API calls (REST/GraphQL) against a
   Postgres-backed schema mirroring the entities above. Each `D.xxx` array
   in the current code becomes a fetch/query.
2. Stand up the integrations the UI is already designed around:
   - **WhatsApp Business API** — the WhatsApp Agent module already models
     inbound message → classification → AI draft → approval → send; swap the
     simulated `messages` array for a webhook-backed inbox.
   - **Calendar / scheduling API** — the Appointment Agent's slot-check logic
     (never double-book) maps directly onto a calendar API's free/busy query.
   - **India Post / courier tracking API** — the Shipment Control Tower's
     `events` timeline is structured to match typical tracking-API payloads
     (status + location + timestamp); swap the generator for a live poller.
   - **Payment gateway** — order `paymentStatus` becomes a webhook-driven
     field from Razorpay/Stripe/etc.
   - **LLM provider** — the "AI interpretation," "suggested response," and
     RAG knowledge-base lookups are currently deterministic templates;
     swap for a real LLM call constrained to the clinic's verified knowledge
     base (see guardrails below), with the same approval gate preserved.
3. Add real authentication and enforce the role/permission matrix (already
   modeled in `ROLES` in `ui.jsx`) server-side, not just in the UI.
4. Add durable audit logging (the current `auditTrail` array becomes an
   append-only table) — this is a healthcare-adjacent app, so treat it as a
   compliance requirement, not a nice-to-have.

## Clinical AI guardrails (enforced in the UI, not just described)

- The WhatsApp Agent never auto-sends a clinical response — every message
  requires **Approve & Send**, **Edit**, **Ask Patient More Questions**, or
  **Escalate** from a human role.
- Red-flag screening (chest pain, breathing difficulty, bleeding, loss of
  consciousness, neurological symptoms, self-harm language, etc.) routes
  straight to an escalation banner and explicitly suppresses AI-generated
  self-care advice.
- Knowledge-base answers always show provenance — **Verified clinic
  knowledge**, **Classical source**, **General informational source**, or
  **AI inference** — and anything not verified is labeled "Reference not
  verified — Vaidya review required" rather than presented as fact. This
  prototype does not fabricate verse/chapter citations.
- The Replenishment Agent only ever produces a draft "Create Purchase
  Recommendation" — nothing is auto-ordered.
- Role-based access is demonstrated live: switch the role selector (top
  right) to Pharmacy Staff or Customer Support and the Business Command
  Center becomes restricted; the AI Agent role itself carries no standing
  permissions in the roles matrix (AI Agents → Roles & permissions).

## Known limitations of this prototype

- Data is regenerated deterministically from a fixed seed — it's the same
  every time you open the app, which keeps the demo stable but isn't "live."
- No backend, no persistence — actions like "Approve & Send" update
  in-memory state for the session only (refreshing resets everything).
- Responsive behavior (breakpoints) depends on Tailwind loading; the offline
  fallback preserves layout and full functionality but not every breakpoint.
- This is a UI/UX and interaction-model prototype, not a certified medical or
  regulatory-compliant system — no claim of HIPAA/DPDP/clinical-software
  certification is made or implied.
